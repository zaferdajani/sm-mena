# Native creator connections and reviewed portfolio import

Prepared 2026-09-29 for Sawwiq, repository zaferdajani/sm-mena. **Implementation specification: not a claim that OAuth or social import is implemented/live.** The companion code change implements onboarding guidance only. Do not add nonfunctional Connect buttons to the user interface or say adding credentials alone makes this specification work.

## Product decision
Use the platforms' native consent-based OAuth/API products. Do not buy a unified social API service, ask creators for passwords/access tokens, collect browser session cookies, scrape around access restrictions, or connect the owner's ChatGPT accounts on behalf of all future creators. Sawwiq registers its developer apps once; each creator then authorizes Sawwiq on the relevant platform's own consent screen.

The experience: Studio -> Connected platforms -> choose provider -> explain read access -> authorize -> explicitly select the authorized channel/Page/account -> say whether it is the creator's own account or a client account they manage -> choose published work -> group related items into a project -> review role, client, cover, caption and publication rights -> publish deliberately. Connecting alone must never publish anything or consume a Founder seat. Connecting is optional; uploads and permitted existing import paths remain usable.

A Google identity, an external social account, a portfolio client, and a work sample are distinct entities. Verified authorization is evidence of access only, not authorship, business verification, client endorsement, exclusive representation or ownership of every asset. Never update isVerified, confirmedAt, review provenance, matching weights or Founder eligibility simply because an OAuth flow succeeds.

Personal-account bulk import is not promised. No DM, ad or publishing permissions in the first release. | Authorized professional account, media selection and reviewed import/display where the API and terms permit it. | Facebook | Facebook Login / Pages API | pages_show_list for selection; pages_read_engagement for the applicable Page content reads. Validate exact endpoint permissions and required Advanced Access/App Review for non-app-role users before enabling. Instagram's Facebook Login configuration is a separate supported alternative and has different Page linkage and scope requirements. Do not mix instagram_basic (Facebook-login configuration) with instagram_business_basic (Instagram-login configuration), and do not implement the discontinued Basic Display product as a fallback. Pin Meta API versions deliberately after checking the version supported by the approved app; do not silently assume the latest version number.

## Reuse current Sawwiq instead of replacing it
- Own profile links currently live in the provider profile editor; client social links in Studio -> Clients through lib/social-links.ts. These stay explicitly unverified URLs, not OAuth connections.
- Portfolio posts use components/studio/post-form.tsx, images + caption/services + optional clientId. The existing manual form accepts images, not arbitrary video files. Keep upload limits, compression, validation, rights and backend ownership checks.
- Existing PDF and Behance import are separate sources guarded by portfolio_import. Preserve their parsers, source credits, review/publish behavior and current controls; do not claim Behance supplies a new OAuth app/API merely because the importer exists.
- Reuse posts/source metadata and portfolio-client CRUD when appropriate. New external video/embedded sources need an explicit supported post/media type with tests, not a forged app-mall embed or raw HTML placed into captions.
- Default titles, source dates or client names inferred from captions are suggestions for review. Never silently create client endorsements or turn every imported image into its own project.

## Required UI
A Connected platforms page should show each provider's capabilities, account prerequisites, permission purpose and precise states: not configured; ready to authorize; selection pending; connected with scopes; limited permission; expired/reconnect; revoked; or failed with a safe explanation. Configuration status is not proof of provider approval; connected status comes only from a completed verified flow. Show last successful check and which resource is connected, and keep account connection separate from public display opt-in.

Before account selection, ask 'My own platform' versus 'A client platform I manage'. A client selection is optional and restricted to the signed-in agency's own portfolio clients. Permit more than one authorized Page/channel when supported, with separate labels. Connection of a managed client account does not auto-publish the client's identity. Present 'Preview what will be public'. Retain separate badges for user-declared role, provider-authorized access and actual client confirmation.

The source browser uses a paginated grid of permitted metadata. One source carousel may become one work sample; selected related posts may form one project if the user chooses. Suggest grouping but require confirmation. Show full supported previews, cover selection, source attribution, the user's contribution, optional evidenced outcomes and client permissions. For unsupported formats or expired sources, explain and offer original-image upload; do not silently fail or pretend video is accepted by the current image form.

Consent is incremental. 'Connect Google' must not simultaneously request YouTube, Gmail, Drive, Facebook and TikTok. 'Import' must not request publish/message/ads permissions. An optional later account-sign-in feature requires separate account-linking safeguards. There is no automatic cross-posting, bulk invitation, posting on a creator's behalf or continuous sync without a separate explicit opt-in.

## Backend boundaries
Use mature, currently maintained provider/OAuth libraries compatible with the installed Next.js version. Read local Next docs and the current repo's auth, session, proxy, validation and rate-limit code before changing them. Do not write a home-grown token verifier when a validated SDK is appropriate. Add no paid vendor without approval.

1. A POST start action verifies the signed-in user, current agency ownership, allowed provider and purpose, and same-origin protections. Generate cryptographically random state. Store only its hash plus initiator user/agency/session binding, provider, purpose, locale and a short expiry in a server-side attempt table. Use PKCE S256 for supported flows; verify provider support rather than adding an unrecognized parameter. Exact HTTPS callbacks are registered in each provider's console; do not derive them from untrusted Host/returnTo input.
2. Callback atomically consumes the matching unexpired attempt, enforces the original browser/session/user/agency/provider binding, checks denial and granted scopes, and exchanges the code server-side. Reject state/provider swaps, replay, expired attempts and a changed logged-in user. Use issuer/audience/signature/expiry/nonce verification for any ID token used for identity; never trust an email or unverified JWT payload. Do not automatically merge existing Sawwiq accounts on an email match or grant staff roles from a provider email.
3. Enumerate permitted resources from the provider response/API; save a short-lived server-side pending selection. Require the creator to confirm a resource actually present in that authorized selection. Never trust a submitted channel/Page/account id or clientId merely because it is syntactically valid. Bind tokens, resources, imported drafts and all read/write queries to the owning agency; test cross-agency isolation on routes, actions, APIs, previews, exports and notifications.
4. Store access/refresh tokens encrypted at rest with authenticated encryption, a dedicated server secret, key version and associated connection/provider/tenant data. Never expose tokens, codes, raw provider responses or secrets to clients, AI, analytics or logs. Public responses use explicit projections, not SELECT * serialization. Missing keys or approvals must disable authorization safely, not select an insecure fallback.
5. Use allowlisted official API endpoints, TLS, no arbitrary redirects, response/size/time limits, bounded pagination, validated ids and content types. Treat captions, metadata and embed URLs as untrusted. Preserve current SSRF protections; never fetch arbitrary user-controlled import URLs with the connection's credential. Do not send source media, customer identities or private fields to AI by default.
6. Token refresh is server-side and serialized/CAS-protected per grant so concurrent workers cannot overwrite rotated tokens. Handle permission loss, expiry, quota errors and revoked access separately. Persist quotas/job deduplication independently of deletable draft/project rows. Network failure is not evidence of account disconnection or of authorization success.
7. Disconnect immediately stops jobs and prevents new reads, then revokes the grant where supported and removes credentials and provider-derived data according to the actual provider/user-deletion policy. Revocation may affect other resources sharing a grant: model that relationship and explain it. If remote revocation fails, record a safe pending state and provide provider-side permission management without falsely claiming revocation. Add verified Meta deauthorization/data-deletion callbacks and other applicable provider revocation handlers before app approval.
8. Refresh or delete cached provider metadata by the provider's applicable policy. YouTube general metadata requires refresh/delete after 30 days; do not assume special extended-storage amendments apply. TikTok cover URLs expire and need refreshed metadata. Apply removal/restriction changes to public embeds and drafts, including existing published source references. Keep user-authored project descriptions and independently uploaded originals distinct from revocable API data and explain what will remain. Retention jobs must work when no user visits a page.

## Proposed data separation (adapt to actual current schema)
- OAuth attempts: hashed state, expiry, consumedAt, initiator/session binding, provider/purpose, sealed verifier; short-lived and purged.
- Grants: owning tenant/user, provider subject id, scope set, sealed tokens/key version, expiry, status, consent version and lastVerifiedAt; private only.
- Resources: grant id, provider resource id (string, not a JavaScript floating-point number), type/channel/Page/account, display metadata + timestamps, explicit own/managed-client classification and optional authorized client binding.
- Import drafts/batches: tenant and resource id, selected stable provider item ids, bounded source metadata, cursor/version, proposed grouping, rights/role review, state and expiry. Creating a draft never creates a public post.
- Published provenance: source provider/resource/item id, original source URL/date, imported/refreshed timestamp, permission/role declaration and supported display mode. Dedupe via database constraints on the intended tenant/source item mapping, not caption, a mutable thumbnail URL or an in-memory Set.

Migrations must be additive, rehearsed on PGlite and disposable Postgres, integrated with the existing Drizzle schema/journal/snapshots, and preserve legacy signed contracts and real profiles. Do not edit historical migrations or run db:reset on production. Fixtures/mock grants must be impossible to enable as real production connections or public verification evidence.

## Execution stages / exact completion labels
S0: inspect current main and add the private connection/grant model, permissions, readiness UI, consent/retention text, durable attempt handling, synthetic provider fixtures and negative tests. Status remains implemented_not_provider_verified until real provider testing succeeds.
S1: implement Google identity linking and a YouTube connection-to-reviewed-public-work flow. Handle no channel, multiple/brand account selection, denied/partial scopes, private/unavailable videos, source credit, disconnect and reauthorization. Do not call this a new Google sign-in path unless that path was separately implemented/tested.
S2: implement Instagram Login for professional accounts and Facebook managed Pages as distinct adapters/consent flows, with approved scopes and required review/deletion endpoints. Personal Instagram should get a clear manual alternative; lack of a Facebook Page must not block the dedicated Instagram Login path.
S3: implement TikTok Login Kit/Display, scope-aware account fields and user-selected public video display. No Content Posting API or raw-video downloading.
S4: unify the permitted source picker and project grouping, verify existing original-upload/PDF/Behance flows, accessible previews, deletion propagation, small-screen rendering and repeated imports. Release a complete supported provider slice independently instead of making the whole site wait for all external reviews.

For every provider track code, CI, registered app, approved permissions, test-user OAuth, production eligibility, authenticated live success and import/delete proof separately. External approval pending is a blocker only to that provider, not permission to fabricate a working button or block first-work publishing.

## Owner/operator configuration (one time, never every creator)
- Google Cloud project: enable YouTube Data API; configure OAuth consent/branding/domain/privacy links, web client and exact callback(s), test accounts, quotas and any verification required for the requested scopes.
- Meta developer app/product(s): Instagram Login and Facebook Pages with their correct credential sets, registered callbacks, suitable business/app verification, exact permissions/access levels and deauthorization/data-deletion URLs.
- TikTok developer app: Login Kit and Display API products, approved scopes, verified domains and exact static HTTPS callback, privacy/terms and required review evidence.
- Store IDs/secrets/encryption keys in the deployment secret manager/Vercel settings only. Never ask the owner or users to paste a secret into chat or a profile form. Do not reuse the existing MFA key for OAuth tokens.
- Proposed environment names and callback routes are to be finalized by the implementing agent, recorded in an example config without values, and matched exactly to the consoles. Do not enable a provider merely because environment strings are present: app review and controlled live testing are separate gates.

## Mandatory acceptance / negative cases
Test both locales at 320/390/768/1440px, keyboard, reduced motion, partial/empty profiles, no configured provider, and all existing routes. Scope/authorization fixtures must include deny, partial consent, unknown account type, no resources, multiple Pages/channels, expired state/code, wrong session, provider swap, callback replay, foreign tenant resource/client, token rotation race, deletion/revocation racing a queued import, provider outages/429, pagination loops, malicious captions/URLs, duplicate imports, expired covers, deleted/private media and public/private preview boundaries. Confirm tokens/codes/PII never appear in browser responses, reports, telemetry or model input. Assert connect/draft actions never publish, post back, message, alter client confirmation or consume seats. Public UI must preserve provider attribution and permitted player controls. Review an actual provider authorization and allowed-media playback; SDK mocks cannot prove OAuth app approval or video decoding.

Before merge: fetch/integrate current main, run full lint/typecheck/unit/build/Playwright, rehearse DB upgrades/rollback and inspect screenshots. Do not weaken existing checks or change Founder/payment/monetization settings. After deployment: canonical /api/version and rendered SHA match the deployed commit; complete a consent-based authenticated provider flow with authorized test accounts and no paid actions. Record exact SHA/run/time/routes/provider modes/scopes/results, with sanitized durable artifacts. External-account testing requires authorization; do not sign up arbitrary real accounts or consume seats to produce evidence.
